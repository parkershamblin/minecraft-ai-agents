# VOYAGER — second-pass deep extraction (appendix, prompts, mechanics)

Model split & sampling (p6): `gpt-4-0314` for curriculum/codegen/critic, `gpt-3.5-turbo-0301` for QA + skill descriptions, `text-embedding-ada-002` for all embeddings. **Temperature 0 everywhere except the curriculum agent at 0.1** ("to encourage task diversity"). This is a near-greedy stack — the prompting techniques below are decoding-compatible with our greedy Ollama setup; what does NOT transfer is freeform JS codegen (p10: "VOYAGER requires the quantum leap in code generation quality from GPT-4, which GPT-3.5 and open-source LLMs cannot provide"; GPT-3.5 codegen ablation gets 5.7× fewer items, p9). Our fixed-verb executor sidesteps exactly that dependency, so everything EXCEPT Prompt 4's "write code" core survives 8B.

## 1. PROMPTS (6 total)

**Prompt 1 — curriculum system prompt (pp21-22).** Purpose: propose the next task. Structure in order: (a) role + goal line: "You are a helpful assistant that tells me the next immediate task to do in Minecraft. My ultimate goal is to discover as many diverse things as possible, accomplish as many diverse tasks as possible and become the best Minecraft player in the world."; (b) "I will give you the following information:" — QA pairs (Question/Answer 1..N), then Biome, Time, Nearby blocks, Other blocks that are recently seen, "Nearby entities (nearest to farthest)", "Health: Higher than 15 means I'm healthy.", "Hunger: Higher than 15 means I'm not hungry.", Position, "Equipment: If I have better armor in my inventory, you should ask me to equip it.", Inventory (xx/36), "Chests: You can ask me to deposit or take items from these chests. There also might be some unknown chest, you should ask me to open and check items inside the unknown chest.", "Completed tasks so far: ...", "Failed tasks that are too hard: ..."; (c) 8 criteria; (d) "You should only respond in the format as described below: RESPONSE FORMAT: Reasoning: ... Task: ..."; (e) ONE few-shot example ("Reasoning: The inventory is empty now, chop down a tree to get some wood. Task: Obtain a wood log."). Load-bearing criteria verbatim (p22):
- 1) "You should act as a mentor and guide me to the next task based on my current learning progress."
- 3) "The next task should follow a concise format, such as 'Mine [quantity] [block]', 'Craft [quantity] [item]', 'Smelt [quantity] [item]', 'Kill [quantity] [mob]', 'Cook [quantity] [food]', 'Equip [item]' etc. It should be a single phrase. Do not propose multiple tasks at the same time."
- 4) "should not be too hard since I may not have the necessary resources or have learned enough skills"
- 5) "should be novel and interesting... I should not be doing the same thing over and over again."
- 6) "I may sometimes need to repeat some tasks if I need to collect more resources to complete more difficult tasks. Only repeat tasks if necessary."
- 7) "Do not ask me to build or dig shelter even if it's at night."
- 8) **the verifiability gate**: "Tasks that require information beyond the player's status to verify should be avoided. For instance, 'Placing 4 torches' and 'Dig a 2x1x2 hole' are not ideal since they require visual confirmation from the screen. All the placing, building, planting, and trading tasks should be avoided."

Criterion 3 IS our task grammar (Mine/Craft/Smelt/Kill/Cook/Equip ≈ gather/craft/hunt); criterion 8 is the design rule that makes rule-based ledger verification possible — copy both.

**Prompt 2 — self-ask questions, GPT-3.5 (pp22-24).** Same goal preamble + observation block, then 4 criteria: "ask at least 5 questions (but no more than 10)... Each question should be followed by the concept that the question is about"; questions must be "specific to a concept in Minecraft" and "self-contained and not require any context"; "Do not ask questions about building tasks". Few-shot is dense: ~7 labeled BAD examples with reasons ("the question requires the context of my current inventory") and 2 GOOD, plus 3 situational templates ("Let's say you see a creeper nearby, and you have not defeated a creeper before. You can ask a question like: Question: How to defeat the creeper? Concept: creeper") and 6 more Q/C pairs with concept-selection annotations ("the above concept should not be 'ore' because I need to look up the page of 'sparse jungle'..."). Output: "Reasoning: ... Question 1: ... Concept 1: ..." repeated.

**Prompt 3 — self-answer, GPT-3.5 (p24).** Four lines: "You are a helpful assistant that answer my question about Minecraft." / info: Question / "You will answer the question based on the context (only if available and helpful) and your own knowledge of Minecraft. 1) Start your answer with 'Answer: '. 2) Answer 'Answer: Unknown' if you don't know the answer." The explicit Unknown escape hatch is the anti-hallucination move — cheap to copy.

**Prompt 4 — code generation (pp26-30).** See §2 for full structure. Output format: "RESPONSE FORMAT: Explain: ... Plan: 1)... 2)... Code: ```javascript // helper functions (only if needed, try to avoid them) ... // main function after the helper functions async function yourMainFunctionName(bot) {...}```". Zero few-shot dialogues; the "few-shot" is the primitive source code itself.

**Prompt 5 — skill description generation, one-shot (pp31-32).** "You are a helpful assistant that writes a description of the given function written in Mineflayer javascript code. 1) Do not mention the function name. 2) Do not mention anything about `bot.chat` or helper functions. 3) There might be some helper functions before the main function, but you only need to describe the main function. 4) Try to summarize the function in no more than 6 sentences. 5) Your response should be a single line of text." One-shot: full `mineCobblestone(bot)` source → "The function is about mining 8 cobblestones using a wooden pickaxe. First check if a wooden pickaxe is in the inventory. If not, craft one. If the wooden pickaxe is available, equip the wooden pickaxe in the hand. Next, explore the environment until finding a stone block. Once a stone block is found, mine a total of 8 cobblestone blocks using the wooden pickaxe." (p32).

**Prompt 6 — critic/self-verification (pp35-37).** Structure: role ("You are an assistant that assesses my progress of playing Minecraft and provides useful guidance."); rubric line worth copying: "You are required to evaluate if I have met the task requirements. Exceeding the task requirements is also considered a success while failing to meet them requires you to provide critique to help me improve."; observation block WITH verification hints inline: "Hunger: My current hunger level. For eating task, if my hunger level is 20.0, then I successfully ate the food.", "Equipment: My final equipment. For crafting tasks, I sometimes equip the crafted item.", "Inventory (xx/36): My final inventory. For mining and smelting tasks, you only need to check inventory."; JSON format EXACTLY:
```
{
    "reasoning": "reasoning",
    "success": boolean,
    "critique": "critique",
}
Ensure the response can be parsed by Python `json.loads`, e.g.: no trailing commas, no single quotes, etc.
```
**7 few-shot examples** (pp35-37), each teaching a verification heuristic: (1) counting across variants ("You have 2 oak logs and 2 spruce logs, which add up to 4 wood logs." → success); (2) have-materials-but-didn't-craft → `"success": false, "critique": "Craft a wooden pickaxe with a crafting table using 3 spruce planks and 2 sticks."`; (3) item-transformation mapping ("Mining iron_ore in Minecraft will get raw_iron. You have 5 raw_iron" → success); (4) which-observation-channel-to-trust ("For planting tasks, inventory information is useless. In nearby blocks, there is farmland and wheat" → success); (5) drop-as-proof ("You have rotten flesh in your inventory, which means you successfully killed one zombie."); (6) hunger==20.0 eating rule; (7) arithmetic-on-state deposit example → false with actionable critique listing which items to deposit. These examples are the technique — a critic is only as good as its evidence-mapping heuristics. Our ledger already does 1/3/5 rule-based; the paper's own failure case (spider string not recognized as combat success, p10) shows why rule-based beats 8B-LLM here.

## 2. MECHANICS

**Control-primitive API (pp24-25) — diff vs our verbs.** Custom primitives (dual purpose: callable AND usage demonstration): `exploreUntil(bot, direction, maxTime = 60, callback)` (direction Vec3 of −1/0/1 components; callback = early-stop predicate polled each second; returns null on timeout); `mineBlock(bot, name, count = 1)` (32-block radius); `craftItem(bot, name, count = 1)` (needs crafting table nearby); `placeItem(bot, name, position)`; `smeltItem(bot, itemName, fuelName, count = 1)` (needs furnace); `killMob(bot, mobName, timeout = 300)`; `getItemFromChest(bot, chestPosition, itemsToGet)`; `depositItemIntoChest(bot, chestPosition, itemsToDeposit)`; plus `checkItemInsideChest(bot, chestPosition)` appearing in the prompt body (p28). Mineflayer passthroughs (p25): `bot.pathfinder.goto(goal)` with `GoalNear(x,y,z,range)`, `GoalXZ(x,z)`, `GoalGetToBlock(x,y,z)`, `GoalFollow(entity,range)`, `GoalPlaceBlock(position,bot.world,{})`, `GoalLookAtBlock(position,bot.world,{})`; `bot.isABed`, `bot.blockAt`; async: `bot.equip(item, destination)` (hand/head/torso/legs/feet/off-hand), `bot.consume()`, `bot.fish()`, `bot.sleep(bedBlock)`, `bot.activateBlock(block)`, `bot.lookAt(position)`, `bot.activateItem()`, `bot.useOn(entity)`. **Diff vs our verb set:** we lack explore-with-stop-predicate, place, smelt, chest deposit/withdraw, equip, consume, sleep, activate/use. The highest-leverage gaps for tech-tree progression are `smeltItem`, `placeItem` (furnace/table placement), `equip`, and chest I/O (enables inter-villager resource handoff — their chest primitives are the only "collaboration channel" in the paper).

**Curriculum mechanics.** Warm-up schedule (Table A.1, p21) — prompt fields gated by completed-task count: core inventory (log/planks/stick/crafting table/furnace/dirt/coal/pickaxe/sword/axe only), equipment, nearby blocks, position at 0; nearby entities at 5; full inventory at 7; recently-seen blocks + biome at 10; health, hunger, time, additional context (QA) at 15. Purpose: keep early prompts small and distraction-free — directly applicable to our 8B context discipline (start villagers with a stripped percept set, widen with competence). Exploration progress representation: nothing numeric — just the two lists "Completed tasks so far:" / "Failed tasks that are too hard:" (p21) fed back each round (pseudocode p19: `get_exploration_progress(get_completed_tasks(), get_failed_tasks())`). Retry policy: at most **4 rounds of code generation per task** (pseudocode comment p19: "try at most 4 rounds before moving on to the next task"; p6), then `add_failed_task`; failed tasks stay visible in-prompt and the curriculum "has the flexibility to reattempt this task at a later time" (p10) — retry is *deferred and implicit*, steered by criterion 6. Our abandon-and-repropose (3 strikes → CHANGE COURSE) is the same pattern with an explicit ban window.

**Skill library entry, end to end.** Add path (p4 Fig 4, p31): verified program → GPT-3.5 writes description (Prompt 5) → key = ada-002 embedding OF THE DESCRIPTION, value = program text. Retrieval path (p4): query = embedding of (GPT-3.5 general suggestion for the new task + environment feedback), top-5 skills pasted into `{retrieved_skills}` slot of Prompt 4. Retrieval accuracy on 309 samples (Table A.4, p42): top-1 80.2±3.0, top-5 **96.5±0.3** — top-5-into-prompt is what makes mediocre retrieval sufficient. Full example (p32), `craftWoodenPlanks`: tries logNames list across 7 wood types, if none in inventory calls `mineWoodLog(bot)` (skill composition), matches plank type to log type by index, `craftItem(bot, plankName, 1)`, `bot.chat` progress lines. Note every example skill (pp32-34) follows one template: *check inventory precondition → acquire/craft prerequisite via another skill → explore for target → act → bot.chat result*; `catchFiveFishSafely` (p34) adds try/catch with retry on "Fishing cancelled". This precondition-check-first template is exactly what our contract clamps do implicitly.

**Codegen prompt structure (Prompt 4, pp26-30), section by section:** (1) role line; (2) "Here are some useful programs written with Mineflayer APIs." — commented `exploreUntil` usage exemplars (with direction heuristics in comments: "use Vec3(0, -1, 0) because iron ores are usually underground"), then FULL SOURCE of the primitives, each headed by a usage comment ("// Mine 3 cobblestone: mineBlock(bot, 'stone', 3);") and embedded warnings ("// You must place a crafting table before calling this function"); (3) pathfinder goal catalog with inline comments; (4-5) other mineflayer sync/async functions with usage constraints as comments; (6) `{retrieved_skills}` placeholder; (7) round-input declaration: "At each round of conversation, I will give you Code from the last round: ... Execution error: ... Chat log: ... Biome: ... Time: ... Nearby blocks: ... Nearby entities (nearest to farthest): Health/Hunger/Position/Equipment/Inventory (xx/36)/Chests/Task/Context/Critique"; (8) response spec: "Explain (if applicable): Are there any steps missing in your plan? Why does the code not complete the task? What does the chat log and execution error imply?" + "Plan: ... The task completeness check is also based on your final inventory." + Code with 11 rules — key verbatim: "Reuse the above useful programs as much as possible... Do not use `bot.dig` directly."; "you should not make strong assumption about the inventory (as it may be changed at a later time), and therefore you should always check whether you have the required items before using them"; "Functions in the 'Code from the last round' section will not be saved or executed. Do not reuse functions listed there."; "Anything defined outside a function will be ignored, define all your variables inside your functions."; "Call `bot.chat` to show the intermediate progress." (this rule GENERATES the environment-feedback channel); "You should select a direction at random every time instead of constantly using (1, 0, 1)"; "`maxDistance` should always be 32... Do not cheat."; "Do not write infinite loops or recursive functions."; "Do not use `bot.on` or `bot.once` to register event listeners. You definitely do not need them."; (9) RESPONSE FORMAT. **Feedback formatting:** environment feedback arrives as "Chat log" — the accumulated `bot.chat()` lines like "I cannot make stick because I need: 2 more planks" (p5); execution errors arrive as "Execution error" with interpreter line refs — "throw new Error(`No item named ${name}`); No item named acacia_axe at line 18: await craftItem(bot, 'acacia_axe', 1);" (p5). Both are plain labeled text sections, no schema.

**QA pipeline temperatures/flow (pp20, 22-24):** self-ask (Prompt 2, GPT-3.5, temp 0) → each Question+Concept → concept optionally retrieves a wiki doc from MineDojo's knowledge base ("using a wiki knowledge base is optional since GPT-3.5 already possesses a good understanding of Minecraft game mechanics", p20) → Prompt 3 answers (temp 0) → QA pairs prepended to curriculum prompt as additional context; the same QA machinery supplies the "Context" field of codegen (component 11, p25) and critic (component 3, p35).

## 3. AXIS FINDINGS a first pass would miss

- **Long-horizon:** the 4-round refinement budget + defer-failed-task + skill persistence is the whole long-horizon engine; max 160 prompting iterations per run (p7). Skill library's value concentrates at the deep end: w/o it, wooden/stone/iron tools still 3/3 but diamond 0/3 (Table 1, p7); it even lifts AutoGPT when transplanted (Table 2, p8). Self-verification is the single biggest component: −73% items when removed (p9) — and its function is stated as deciding "when to move on to a new task or reattempt a previously unsuccessful task" (p9), i.e., the critic is a *scheduler*, not just a grader. Our ledger plays this role rule-based.
- **Verifiability-first task design** (criterion 8, p22): they constrain the TASK SPACE to what the critic can check from inventory/status. For our race/tech-tree goals: only propose goals checkable from ledger events.
- **Reactivity: essentially absent.** Programs are blocking; no event listeners allowed (rule 10, p30); death is handled out-of-band — "If the bot dies, it is resurrected near the closest ground, and its inventory is preserved for uninterrupted exploration. The bot recycles its crafting table and furnace after program execution." (B.1, p38). Curriculum explicitly forbids sheltering at night (criterion 7). Nothing here helps our 30s-tick danger problem.
- **Collaboration: none** (single agent). The only multi-agent-usable machinery is the chest primitives + chest state in prompts ("unknown chest" exploration nudge, p21) — a ready-made pattern for structured villager-to-villager resource handoff via shared chests, which fits our "structured state, not chat" verdict.
- Baseline re-implementations (B.2, p38): AutoGPT replans task decomposition "if three consecutive subgoals do not result in acquiring a new item" — a 3-strike replan rule nearly identical to our abandon-and-repropose streak.
- Robustness: gpt-4-0314 vs -0613 roughly identical curves (Fig A.4, p42) — the method isn't checkpoint-tuned.
- Failure modes to expect at 8B (p10): curriculum hallucinating unachievable items ("copper sword"); critic missing drop-evidence mappings (spider string). Both argue for our game-data-validated task grammar + rule-based verification.

## 4. REFERENCES TO CHASE

1. **DEPS — "Describe, Explain, Plan and Select"** (Wang et al., arXiv:2302.01560, 2023, p13/p38): interactive planner that reached diamond in Minecraft with feedback+inventory observations only (Table A.2, p38 shows it's the closest system design to ours: no demos, no rewards); its explain-then-replan loop is a 30s-tick-friendly alternative to codegen.
2. **Plan4MC** (Yuan et al., arXiv:2303.16563, 2023, p16): skill graph + planning over a FIXED skill set for long-horizon Minecraft tasks — the fixed-verb analogue of Voyager's library; directly relevant to our verb-plan skill-library candidate.
3. **DECKARD** (Nottingham et al., "Do embodied agents dream of pixelated sheep?", 2023, p15 — no arXiv id printed): LLM hypothesizes a tech-tree world model (Abstract World Model) to guide exploration; the cheapest way to get dragon-directed curriculum without frontier codegen.
4. **MineDojo** (Fan et al., arXiv:2206.08853, 2022, p12): source of the wiki knowledge base used by the QA pipeline; its internet-scale Minecraft corpus is the retrieval substrate if we add a knowledge-lookup step for 8B models that lack game knowledge.
5. **CLAIRIFY** (Skreta et al., "Errors are useful prompts", 2023, p18 — id truncated in print): RULE-BASED verifier iteratively feeding error text to the LLM — published validation of our ledger-as-critic architecture over LLM self-verification.
6. **LEVER** (Ni et al., arXiv:2302.08468, 2023, p17): trains a small verifier on execution results to reject bad programs — a candidate offline-SFT target for our consumer GPU (verifier, not policy — cheaper than MINDcraft-style policy SFT).
7. **Reflexion** (Shinn et al., arXiv:2303.11366, 2023, p14): the baseline Voyager's self-verification supersedes ("more comprehensive than self-reflection by both checking success and reflecting on mistakes", p5); scored 0/3 on everything in-domain (Table 1, p7) — evidence that reflection WITHOUT grounded success-checking is dead weight; do not spend tick budget on it.
