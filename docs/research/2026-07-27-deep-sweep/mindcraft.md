# MINDcraft (arXiv:2504.17950) — second-pass extraction: prompts, mechanics, appendices

Paper: "Collaborating Action by Action: A Multi-agent LLM Framework for Embodied Reasoning" (White, Nottingham et al., UCSD, Apr 2025). 28pp. Framework repo: github.com/kolbytn/mindcraft (p5 fn).

## 1. PROMPTS (§7, pp12–13; live variants pp14, 18–19)

**7.1 General conversing prompt (p12).** Section order: (1) identity+goal line, (2) `$TASK_INVENTORY`, (3) behavior paragraph, (4) `Summarized memory:'$MEMORY'`, (5) `$STATS`, (6) `$INVENTORY`, (7) `$COMMAND_DOCS`, (8) `$EXAMPLES`, (9) `Conversation Begin:`. The behavior paragraph is the technique — verbatim:

> "You are a task-focused Minecraft bot named $NAME. Your current task is: $TASK_GOAL … Act focused on completing your assigned task while being human-like. Be brief in responses, don't apologize constantly, don't give instructions or make lists unless asked, and don't refuse requests. Don't pretend to act, use commands immediately when requested. Do NOT say this: 'Sure, I've stopped.', instead say this: 'Sure, I'll stop. !stop'. Do NOT say this: 'On my way! Give me a moment.', instead say this: 'On my way! !goToPlayer('playername', 3)'. Focus on completing the assigned task efficiently."

The contrastive **"Do NOT say X, instead say Y"** pairs are the anti-"pretend-to-act" fix: chat and command share ONE output channel, and the pairs teach the model that every promise must carry its command inline. This survives 8B (it's the exact prompt the SFT-8B and 70B agents ran with).

Live task prompts (p14) append per-domain hints worth copying: searching hint "search thoroughly for needed resources (with searchForBlocks parameters like 64,128,256)"; identity guard "Respond only as Jill_0, never output '(FROM OTHER BOT)' or pretend to be someone else"; and the no-op protocol: **"If you have nothing to say or do, respond with an just a tab ' '."** — a cheap idle token instead of forced babble. Closer: "This is extremely important to me, take a deep breath and have fun :)".

**Few-shot examples (§7.1.1–7.1.3, p12).** One multi-turn example per domain (3 total), formatted as `Your output:` / `User input: name: (FROM OTHER BOT)…` / `System output:` transcript, each showing chat+command fusion (`!startConversation`, `!inventory`→`!givePlayer`→`!craftItem`, `!checkBlueprintLevel(0)`→`!newAction`→re-check loop). Selected at runtime by **embedding similarity to the current conversation** ("retrieving and prompting with few-shot examples showing usage of our tools via embedding similarity … embodied Retrieval Augmented Generation", p5). Ablation: removing few-shots drops 70B crafting 36%→12% (Table 7, p22).

**7.1.4 Coding prompt (p12)** — used only inside `!newAction`. Sections: identity/task/inventory, codeblock instructions, `$SELF_PROMPT`, `Summarized memory:'$MEMORY'`, `$STATS`, `$INVENTORY`, `$CODE_DOCS`, `$EXAMPLES`, `Conversation:`. Load-bearing verbatim: "write a js codeblock that controls the bot ``` using this syntax ```. The code will be executed and you will receive its output. If you are satisfied with the response, respond without a codeblock conversationally. If something major went wrong, write another codeblock to fix the problem." … "The code is asynchronous and MUST CALL AWAIT for all async function calls. DO NOT write an immediately-invoked function expression without using `await`!! DO NOT WRITE LIKE THIS: ```(async () = {console.log('not properly awaited')})();```" … "Do not use commands !likeThis, only use codeblocks." … "This is extremely important to me, think step-by-step, take a deep breath and good luck!" (Note: our fixed-verb/trusted-executor design deliberately excludes this path; it's also the least 8B-safe part.)

**7.1.5 Initial message (p13)**, injected on world join: *"Immediately start a conversation with other agents and collaborate together to complete the task. Share resources and skill sets."* — collaboration is prompted, not emergent.

**Memory summarization**: no template is printed anywhere in the paper. Known: cadence = **every 15 steps**, style = "summarizing past interactions in a goal oriented manner" (Table 7 caption, p22); it is the single biggest prompting component (36%→12% without it). Output format, from live snapshots: terse first-person state — "Collaborating with Andy_0. Furnace at (731, -59, -1515). Have cooked_rabbit, brown_mushroom, bowl. Need red_mushroom from Andy_0 to craft mushroom_stew. Waiting for red_mushroom to complete task." (p14); the 4-agent example (p18) shows the same shape carrying who-owns-which-subtask. Pattern: partners, landmark coords, holdings, outstanding needs, waiting-on. Directly transplantable as a reflection-prompt spec for our memory-service.

## 2. MECHANICS

### Full 47-command vocabulary (Table 8, pp26–28)

Queries (p26): **!stats** (location/health/hunger/time) · **!inventory** · **!nearbyBlocks** · **!craftable** (craftable with current inventory) · **!entities** (nearby players/entities) · **!modes** (list automatic behaviors + on/off) · **!savedPlaces** · **!getCraftingPlan**(targetItem:str, quantity:num) — full ingredient breakdown + missing-items analysis vs current inventory · **!help**.

Meta/control (p26): **!newAction**(prompt:str) — code-gen escape hatch, "Make a detailed step-by-step plan" · **!stop** (force-stop all actions) · **!stfu** ("Stop all chatting and self prompting, but continue current action") · **!restart** (agent process) · **!clearChat**.

Navigation (p26): **!goToPlayer**(player_name, closeness) · **!followPlayer**(player_name, follow_dist) — endless follow · **!goToCoordinates**(x,y,z,closeness) · **!searchForBlock**(type, search_range) — find AND go to nearest · **!searchForEntity**(type, search_range) · **!moveAway**(distance).

Places/items (p27): **!rememberHere**(name) · **!goToRememberedPlace**(name) · **!givePlayer**(player_name, item_name, num) · **!consume**(item_name) · **!equip**(item_name) · **!putInChest**(item_name, num) · **!takeFromChest**(item_name, num) · **!viewChest** · **!discard**(item_name, num) · **!collectBlocks**(type, num) · **!craftRecipe**(recipe_name, num — "number of times to craft the recipe … NOT the number of output items") · **!smeltItem**(item_name, num) · **!clearFurnace** · **!placeHere**(type) — "Do NOT use to build structures, only … single blocks/torches" · **!attack**(type) — nearest entity of type.

Combat/world/social (p28): **!attackPlayer**(player_name) · **!goToBed** · **!activate**(type) — nearest object (doors/levers/buttons) · **!stay**(seconds, −1 forever) — "Pauses all modes" · **!setMode**(mode_name, on:bool) — "A mode is an automatic behavior that constantly checks and responds to the environment" · **!goal**(selfPrompt) — "endlessly work towards with continuous self-prompting" · **!startConversation**(player_name, message) · **!checkBlueprintLevel**(levelNum) · **!checkBlueprint** · **!getBlueprint** · **!getBlueprintLevel**(levelNum) · **!endConversation**(player_name).

Diff vs our 9 verbs — a beat-the-game agent additionally needs: chest I/O (3 cmds), give-item (their #1 collaboration primitive), equip, consume, place-single-block, activate (doors!), sleep, named-waypoint memory (rememberHere pair), search-then-go primitives, a crafting-plan oracle (getCraftingPlan is rule-based, zero LLM cost — analog of our ledger checks), and the two orthogonal control planes: **modes** (rule-based reactive layer under the LLM — their answer to fast danger, no 30s-tick dependency) and **goal** (self-prompting long-horizon layer above it).

### Conversation manager (§3.3, p5)
Agents open/close channels at will via `!startConversation`/`!endConversation`. On receiving a message an agent may "respond immediately, ignore it, take another action, or speak to another bot." Hard limit: **only two agents per conversation**; N-agent coordination = serially transitioning between pairwise conversations (prompted explicitly: "talk to all the agents using startConversation … instead of talking to just one agent", p19). **Action/dialogue interlock**: if both parties are executing actions, the conversation is *paused* until actions finish; if one is acting, it is *slowed* (rate-limited). Routing format: inbound = user-role `"Name_0: (FROM OTHER BOT)<text>"`; command results = system-role `"Code output:\n…"`; guard rail when misused: system message "You are already in conversation with Andy_0. Don't use this command to talk to them." (pp14,16,19–20). Note pp20 failure trace: `endConversation` delivers a final message to the other party ("Conversation with Bob_0 ended with message: …").

### SFT dataset construction (p6 Table 2, p7, §9 p13)
Oracle: **llama3.3-70b-instruct** (chosen for open weights/reproducibility; "such an oracle agent can be any other LLM or even a human player", p7). Pipeline: (1) run 200–2000 trials per domain on TRAIN tasks; (2) filter — cooking/crafting keep only score=1 runs; construction keep top-25%-of-edit-distance runs; (3) **each transition in a kept trajectory = one training row**. Row shape (§9, p13, exact): context = *"Everything before 'Response:'"* = the FULL general prompt ("the instructions, the consolidated memory, the agent's stats, the command docs, and in-context examples") + the conversation array of role-tagged turns up to now; target = the next assistant turn (chat text and/or one-or-more `!commands` — see p15: target is two stacked `!givePlayer` calls; p16: chat+`!craftRecipe` fused). Multi-turn episodes become rows by sliding the cut to each assistant turn, memory snapshot included as-of-that-moment. Volumes: cooking 635 trials→103 successes→3,975 transitions (avg traj 29.7); crafting 1,645→158→3,565 (19.2); construction 211→52→9,228 (111.5); ≈16k examples from ~200 successful runs (p2). Result (Table 3, p7): llama3-8b 0.00→**0.28** crafting (beats gpt-4o 0.17, 70B 0.16), 0.01→0.18 cooking, 0.00→0.20 construction. **No training hyperparameters (LoRA/lr/epochs) appear anywhere in the paper** — for our exporter we get the data shape but must source training config elsewhere. For our ledger exporter: their "consolidated memory" field ≈ our reflection state; their system "Code output" turns ≈ our ActionCompleted/ActionFailed events; the win filter ≈ our honesty-gated race wins.

### Task generation, splits, blueprints (§4 p6, §8 p13, §11 pp24–25)
Train/test anti-pollution: construction = disjoint procedural seeds; cooking/crafting = **goal-item split** (train: cooked_beef, cooked_porkchop, cooked_chicken, cooked_rabbit, beetroot_soup, rabbit_stew, suspicious_stew, cookie, pumpkin_pie, golden_apple; test: cooked_mutton, baked_potato, cake, golden_carrot, mushroom_stew, bread — p24 §11.2). Task spec is one YAML entry (p24 §11.1): task name, goal string, agent names, agent count, per-agent initial inventory, target item, target count, task type, timeout seconds. Construction naming: `materials_{m}_rooms_{r}_window_{w}_carpet_{c}_variant_{v}`, each 0–2 = relative complexity (p13). Defaults: 2 agents, 10-min timeout +5 min per room level, cheats off (p13 §8.2). **Blueprint representation is level-sliced (y-layers) with a diff API**: `!checkBlueprintLevel(n)` returns "Level 1 requires the following fixes: Place terracotta at coordinates X:155, Y:-59, Z:-168 … Remove the terracotta at X:155, Y:-59, Z:-166" (p16) — the environment does the spatial diffing, the LLM never reasons about geometry (consistent with VoT regressing at 8B; spatial truth stays code-side). Scoring: edit distance to blueprint / % blocks correct as floating reward (p6, p24 §11.3). Validation: per-round check in agent.js; inventory-presence for cooking/crafting (0/1), bots kicked on completion (p24). Reset: clear inventories + teleport to new random location; crafting=Forest biome with materials in place; cooking=generated farm world (livestock, crops, furnace, smoker, chest with hard-to-procure items like milk); construction=Superflat Y=−60 (p25). Hell's Kitchen: each agent's process is separate — cross-agent progress resolved by **writing partial progress to a file** (p25).

## 3. AXIS FINDINGS beyond a first pass

- **More agents = worse, monotonically** (Fig 3a/b, pp7–8): tasks are parallelizable, yet success falls "from upto 90% down to less than 30%" going 2→5 agents, all models. Bottlenecks named: redundant work, resource contention ("only enough milk for one cake"), station contention ("they can't all use the furnace at the same time"), and "effectively communicating which agent has already what and not getting in each other's way" (p8). For our 6-villager fleet: cap concurrent collaborators per objective; assign disjoint resources structurally, don't negotiate them.
- **Plan communication is the cliff, and SFT doesn't fix it at 8B**: forcing plan communication drops all models >15% (Fig 3c/d, p8). Cooking by recipe access (Table 5, p23): llama3-8b-sft 41.67% (no block) → 16.67% (1 blocked) → **0.00% (both blocked)**; even Claude falls 91.67→66.67. Confirms the program stance: structured state must carry plans; NL relay of multi-step plans is dead on our model class even after SFT.
- **Prompt ablation (Table 7, p22, 70B crafting)**: Full 36% · no memory 12% · no few-shot 12% · no communication 0%. Goal-oriented memory summarization every 15 steps and retrieved few-shots are each worth 3×; communication is existential (it's a collaboration task).
- **SFT is non-monotonic in depth** (Table 4, p23): 8b-sft depth-0 38.46%, depth-1 **66.67%**, depth-2 33.33% — trained competence transfers best at moderate recipe depth.
- **Destructive interference on shared structures**: "agents … place a layer of stone blocks only to have other agents completely destroy it" (p7, §10.1 p19 w/ video link). Any shared-build feature needs ownership partitioning (per-level or per-region claims in our ledger).
- **Reactivity architecture**: LLM never handles fast events — **modes** run as "automatic behavior that constantly checks and responds to the environment" (p28), pausable via `!stay`; `!stfu` decouples chat from an in-flight action. Maps to our GuardTether pattern: keep reactive rules in minecraft-service, below the tick.
- **Failure taxonomy at small scale** (pp19–22, verbatim traces): ownership confusion (Andy asks Jill for sugar cane Bob holds); phantom-requirement invention ("we still need tinder" — hallucinated item); **gift ping-pong** (Jill returns gold nuggets Andy just gave her, p22); acting on assumed rather than verified inventory (compass, p21). All are state-tracking failures our ledger/relationship store can adjudicate rule-side.
- **Vision doesn't pay**: "vision inputs do not dramatically affect performance … thorough textual observations often outperform visual inputs" (p4). Pull-based text queries chosen explicitly to cut context length (p4, citing Selective Perception [25]).

## 4. REFERENCES TO CHASE

1. **MAGDI** — Chen et al., ICML 2024. Structured distillation of multi-agent interaction *graphs* into smaller LMs. The strongest pointer for our ledger→SFT exporter: distill coordination structure, not chat transcripts, into 8B. (p10, [24])
2. **Optima** — Chen et al., arXiv:2410.08115. Trains LLM multi-agent systems for communication *efficiency* + effectiveness — the fix direction for the plan-communication cliff. (p10, [22])
3. **MALT** — Motwani et al., arXiv:2412.01928. Multi-agent LLM post-training (generator/verifier/refiner roles); relevant if we ever train role-specialized villagers. (p10, [23])
4. **Selective Perception** — Nottingham et al., NAACL 2024. Learning concise state descriptions for LM actors — direct guidance for slimming our percept sections at 8192 ctx. (p10, [25])
5. **CoELA / "Building cooperative embodied agents modularly"** — Zhang et al., ICLR 2024. Modular perception/memory/communication/planning agent, the architecture MINDcraft iterates on; closest published analog to our service decomposition. (p10, [20])
6. **"Why do multi-agent LLM systems fail?"** — Cemri et al., arXiv:2503.13657. Failure taxonomy for MAS; useful checklist against our ledger failure codes. (p9, [1])
7. **PARTNR** — Chang et al., arXiv:2411.00081. Large human-AI embodied collaboration benchmark; task-spec formats worth borrowing for governance-arc tasks. (p9, [8])

**8B-survivability summary**: the conversing prompt, contrastive Do-NOT pairs, tab-noop, 15-step goal-oriented memory summary, pull-based observation queries, rule-based getCraftingPlan/blueprint-diff oracles, modes layer, and success-filtered SFT (0.00→0.28 with ~3.5k transitions) all survive local 8B greedy. What does NOT: the `!newAction` JS code-gen path (70B/frontier oracle territory), NL plan relay (dead at 8B even post-SFT, Table 5), and >2-agent NL coordination (degrades for every model tested).
